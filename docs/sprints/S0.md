# S0 — Fundaciones (bitácora)

Fecha: 2026-11-17 · Rama: `cc/dev` · Estado: **local completo; falta el despliegue en la nube**
(requiere las cuentas de Supabase, Render y Vercel).

## 1. Objetivo

Dejar un esqueleto que arranque igual en cualquier computadora y compruebe por sí solo
que está sano, antes de escribir ninguna función de la clínica.

## 2. Decisiones

| Decisión | Por qué |
| --- | --- |
| Monolito modular hexagonal ([ADR-0001](../adr/0001-monolito-modular-hexagonal.md)) | Dos desarrolladores, una clínica: menos piezas que operar |
| Dos perfiles con el mismo código y las mismas imágenes ([ADR-0002](../adr/0002-perfiles-local-y-nube.md)) | Demostrar portabilidad con evidencia desde el primer día |
| Cola de notificaciones en Postgres ([ADR-0003](../adr/0003-postgres-como-cola-sin-redis.md)) | Sin Redis que administrar en la clínica |
| Python 3.13, FastAPI, SQLAlchemy 2 asíncrono, asyncpg, Alembic, `uv` | Lo indicado en el anteproyecto; `uv.lock` fija las versiones |
| Configuración solo por variables de entorno (`pydantic-settings`); la app no arranca si falta `DATABASE_URL` | Un error de configuración debe verse al iniciar, no en medio de una operación |
| `postgresql://` y `postgres://` se convierten a `postgresql+asyncpg://` | Supabase y Render entregan la cadena sin el driver |
| `/health` (el proceso vive) separado de `/health/ready` (la base responde) | Docker y el monitor externo distinguen "proceso caído" de "base caída" |
| Logs en JSON con identificador de petición, sin parámetros de consulta ni cuerpos | Regla de privacidad: ningún dato clínico en los logs |
| Un único formato de error `{"error": {code, message, request_id}}`; el 422 indica dónde falló, nunca el valor | El frontend maneja un solo formato y no se filtran datos |
| Migraciones con comando explícito, no al arrancar la API | Un arranque no debe modificar el esquema por sorpresa |
| `app.main:create_app` como fábrica, sin instancia global | Las pruebas construyen la app con su propia configuración |
| El `worker` es un esqueleto que verifica la base y se detiene ordenadamente | Deja el cuarto proceso del Compose listo para S7 |
| Frontend movido a `frontend/` en un commit aparte | Monorepo; se puede revertir sin tocar el resto |

## 3. Cambios

### Estructura

```
backend/   app/{main.py, worker.py, shared/, modules/}  migrations/  tests/  Dockerfile
frontend/  (el proyecto de Quasar, sin cambios de contenido) + Dockerfile
deploy/    docker-compose.local.yml  nginx/default.conf  env/*.example
docs/      adr/  sprints/  campo/
.github/workflows/ci.yml
```

### Endpoints

| Método | Ruta | Respuesta |
| --- | --- | --- |
| GET | `/health` | `200 {"status": "ok"}` |
| GET | `/health/ready` | `200 {"status":"ok","database":"up","profile":"local"}` o `503 {"status":"unavailable","database":"down",...}` |
| GET | `/api/health`, `/api/health/ready` | Los mismos, a través de nginx |

### Variables de entorno

| Variable | Valor por defecto | Para qué |
| --- | --- | --- |
| `DATABASE_URL` | obligatoria | Conexión a Postgres |
| `APP_PROFILE` | `local` | `local` o `cloud` |
| `CORS_ORIGINS` | vacío | Orígenes permitidos, separados por comas (solo nube) |
| `STORAGE_BACKEND` | `local` | `local` o `supabase` (se usa desde S5) |
| `STORAGE_LOCAL_PATH` | `/srv/uploads` | Carpeta de imágenes en el perfil local |
| `LOG_LEVEL` | `INFO` | Nivel de logs |
| `WORKER_POLL_SECONDS` | `30` | Intervalo del ciclo del worker |

## 4. Pruebas

- 23 pruebas automáticas, **93,5 % de cobertura** (mínimo exigido: 80 %), incluida la
  migración que sube y baja contra un Postgres real.
- `ruff` (lint y formato) y `mypy --strict` sin errores. Frontend: `npm run lint` y
  `npm run build` sin errores tras moverlo.
- Contenedores: construcción de las dos imágenes (backend 299 MB, frontend 80 MB), los
  cuatro procesos arrancan y quedan sanos, y se probó a mano lo siguiente:

| Prueba | Resultado |
| --- | --- |
| `GET /` por nginx | 200, título "SmileOS" |
| `GET /api/health` y `/api/health/ready` | 200 y `database: up` |
| Ruta inexistente | 404 con el formato único de error |
| `alembic upgrade head` desde el contenedor | Migración `0001` aplicada |
| Usuario del proceso en `api` y `worker` | `uid=10001 (app)`, sin privilegios |
| Se apaga la base de datos | `/health` sigue en 200; `/health/ready` pasa a 503; el worker registra el fallo y sigue vivo |
| Se vuelve a encender | Todo se recupera sin reiniciar nada; la versión de Alembic persiste |
| `SIGTERM` al worker | Se detiene de forma ordenada, código de salida 0 |

## 5. Problemas encontrados y cómo se resolvieron

| Problema | Causa | Solución |
| --- | --- | --- |
| La imagen del frontend fallaba en `npm ci` | El `postinstall` (`quasar prepare`) necesita `quasar.config.js`, que aún no estaba copiado | `npm ci --ignore-scripts`; `quasar build` hace su propia preparación |
| La cobertura marcaba sin ejecutar código que sí se ejecutaba | SQLAlchemy asíncrono corre en *greenlets* | `concurrency = ["greenlet", "thread"]` en la configuración de cobertura |
| Aviso de Alembic sobre `prepend_sys_path` | Falta `path_separator` | `path_separator = os` en `alembic.ini` |
| Un error al apagar el worker en una prueba manual | Se enviaron dos `SIGTERM` (al envoltorio de `uv` y al proceso) | Con una sola señal sale limpio con código 0; no es un defecto del worker |
| Las construcciones de Docker no salían a internet en el entorno de pruebas | Ese entorno solo permite salir por un proxy | Se construyó desde una copia temporal con la CA del proxy; los Dockerfile del repositorio no cambian |
