# S1 — Identidad (bitácora)

Fecha: 2026-11-21 · Rama: `cc/dev` · Estado: **completo en el backend**; falta que el frontend
use la API (hoy su login acepta `admin`/`admin` sin llamar al servidor).

## 1. Objetivo

Que el sistema sepa quién es cada persona y qué puede hacer, antes de construir los módulos
clínicos, y que toda acción de administración deje rastro.

## 2. Decisiones

El detalle y las alternativas están en el [ADR-0004](../adr/0004-autenticacion-propia-jwt-y-refresh-rotativo.md).

| Decisión | Por qué |
| --- | --- |
| Acceso JWT de 15 minutos; refresco opaco, rotativo, guardado como SHA-256 | Funciona igual en local y nube; una base filtrada no sirve para entrar |
| Roles y estado activo se leen de la base en cada petición | Desactivar o cambiar de rol aplica de inmediato |
| Argon2id, mínimo 10 caracteres, sin reglas de composición | Recomendación actual: el largo pesa más que los símbolos |
| La misma respuesta y el mismo tiempo para correo inexistente y contraseña mala | No revelar qué correos existen |
| Detección de reuso del refresco: se revocan todas las sesiones | Un token robado y usado por otro queda inservible |
| Siempre queda un administrador activo; nadie se desactiva a sí mismo | Evita dejar el sistema sin quien lo administre |
| `roles` con el código como llave (tres valores fijos) | Más simple que un UUID sin perder la integridad referencial |
| La bitácora se protege con un disparador de la base | Vale también cuando la aplicación se conecta como dueña de las tablas |
| Validación de correo mínima, sin `email-validator` | Un correo interno como `admin@clinica.local` debe ser válido |
| Primer administrador por CLI, con la contraseña por teclado o variable de entorno | Nunca una contraseña fija en el código |
| Primer módulo con las cuatro capas (`identity`) y `audit` como módulo propio | Establece el patrón que seguirán los demás módulos |

## 3. Cambios

### Endpoints

| Método | Ruta | Rol | Respuesta |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/login` | público | 200 con `access_token`, `refresh_token`, `expires_in` y `user`; 401 `invalid_credentials` |
| POST | `/api/v1/auth/refresh` | público | 200 con un par nuevo; 401 `invalid_token` |
| POST | `/api/v1/auth/logout` | sesión | 204 (idempotente) |
| GET | `/api/v1/auth/me` | sesión | 200 con el usuario |
| POST | `/api/v1/auth/change-password` | sesión | 204; 422 `wrong_current_password` o `weak_password`; cierra las demás sesiones |
| GET | `/api/v1/users` | admin | Página con `items`, `total`, `page`, `per_page`; filtros `active`, `page`, `per_page` |
| POST | `/api/v1/users` | admin | 201; 409 `email_already_exists`; 422 `weak_password` |
| PATCH | `/api/v1/users/{id}` | admin | 200; 404 `user_not_found`; 409 `last_admin` |
| POST | `/api/v1/users/{id}/deactivate` | admin | 200; 409 `self_deactivation` o `last_admin`; revoca sus sesiones |
| POST | `/api/v1/users/{id}/activate` | admin | 200 (añadido al plan: sin él un usuario desactivado no podría volver) |
| GET | `/api/v1/roles` | admin | Los tres roles con su descripción |
| GET | `/api/v1/config/public` | público | `profile` y `features.patient_portal` |

### Base de datos (migración `0002`)

| Tabla | Contenido y restricciones |
| --- | --- |
| `roles` | Llave `code`; sembrada con `admin`, `odontologo`, `recepcion` |
| `users` | Correo único y en minúsculas (restricción `CHECK`); `password_hash`; `is_active`; `last_login_at` |
| `user_roles` | Llave compuesta usuario-rol; se borra en cascada con el usuario |
| `refresh_tokens` | `token_hash` único; `expires_at`; `revoked_at` |
| `audit_log` | Solo inserción (disparador contra `UPDATE` y `DELETE`); `details` en `jsonb`; el usuario no se puede borrar mientras tenga auditoría |

### Variables de entorno nuevas

| Variable | Defecto | Para qué |
| --- | --- | --- |
| `JWT_SECRET` | obligatoria, mínimo 32 caracteres | Firma de los tokens de acceso |
| `ACCESS_TOKEN_MINUTES` | `15` | Vida del token de acceso |
| `REFRESH_TOKEN_DAYS` | `7` | Vida del token de refresco |
| `FEATURE_PATIENT_PORTAL` | `false` | Portal del paciente (en pausa); lo consulta el frontend |

También: comando `python -m app.cli create-admin` y la nueva dependencia de `argon2-cffi` y `pyjwt`.

## 4. Pruebas

- 113 pruebas automáticas con **98 % de cobertura** (mínimo 80 %); `ruff` y `mypy --strict` sin errores.
- Una prueba compara los modelos con las migraciones: si alguien cambia un modelo y olvida la migración, falla.
- Seguridad cubierta por pruebas: token expirado, firmado con otra clave, de otro tipo, sin
  reclamaciones obligatorias, con `alg: none` o emitido en el futuro; reuso de refresco;
  contraseñas y tokens ausentes de la auditoría; bitácora imposible de modificar o borrar;
  carrera de dos altas simultáneas con el mismo correo resuelta por la base de datos;
  cada endpoint de administración rechaza a los roles `odontologo` y `recepcion`.
- Verificación manual por HTTP con el servidor real: migración, `create-admin`, inicio de
  sesión, alta de recepción, 403 de recepción en la lista de usuarios, rotación y reuso de
  refresco, configuración pública y rutas de OpenAPI. Los logs no contienen contraseñas ni tokens.
- Contenedor: la imagen del backend se reconstruye (302 MB), corre sin privilegios y dentro
  de ella funcionan `alembic`, el CLI, `/health/ready` y el inicio de sesión.
  No se volvió a levantar el Compose completo de cuatro procesos (el S1 solo cambió el
  backend y las variables de entorno); `docker compose config` valida y avisa si falta `JWT_SECRET`.

## 5. Problemas encontrados y cómo se resolvieron

| Problema | Causa | Solución |
| --- | --- | --- |
| Una prueba del JWT fallaba al validar un token emitido por un reloj de prueba | PyJWT comparaba `iat` con el reloj real del sistema | Se desactivó esa verificación y se valida `exp` e `iat` con el reloj inyectado, con 60 s de tolerancia |
| `email-validator` rechazaría `admin@clinica.local` | Considera inválidos los dominios de uso especial | Se retiró la dependencia y se usa una validación simple |
| Varias líneas del servicio de contraseñas quedaban sin cubrir | Faltaban pruebas de la carrera de altas, del hash antiguo y de la idempotencia | Se agregaron las tres pruebas |
| La copia local del repositorio desapareció al reiniciarse el entorno | El entorno de trabajo es temporal | Se clonó de nuevo `cc/dev` desde GitHub; no se perdió ningún commit |
